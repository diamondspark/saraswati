# Saraswati Phase 1 security audit

This document assembles the findings of four independent, read-only security
reviews of the pinned Metrolist base (upstream `main` @ `76fa5a78`, InnerTubeX
`v0.8.4`) into one table per review area, replaces each auditor's *tentative*
disposition with the *real* one — verified against the code actually on
`phase1-harden` as of this task — and records what is still open today.

## Method

**Reviewers.** Four read-only area auditors (Claude, opus) reviewed the pinned
base commit on 2026-10-17, in parallel, with no ability to build, run or
modify anything (Ruling R9):

- **A — platform and IPC surface:** manifest, exported components, FileProvider,
  backup scope, `PendingIntent` flags, secrets in `BuildConfig`/resources.
- **B — web content, sign-in, untrusted input:** `LoginScreen.kt`'s WebView,
  `PoTokenWebView`, the cookie's lifecycle, the proxy setting, deep links.
- **C — data, backup/restore, logging, third-party libraries.**
- **D — YouTube engine, remote configuration, network host inventory** (also
  produced the standalone `host-inventory.md` appended below).

**Tools.** Each auditor's own method section (quoted in `audit/findings-*.md`)
states the review was static source reading with `rg`/`grep`/`sed`/`git grep`
over the app, the `innertube` module and the InnerTubeX `v0.8.4` source tree;
one check (Media3's `ControllerInfo` API surface) was done by `unzip`/`strings`
on a cached AAR, deleted afterwards. **Nothing was built, run or installed**
for the audit itself — no `rea-agents` CLI invocation appears in any of the
four method sections, despite the task brief describing that as the intended
evidence source; this is noted here rather than silently reconciled. Base
commits: app `76fa5a78b5110674442884b6f21c0cef51cdb782` (2026-10-08 upstream
date), InnerTubeX `v0.8.4` (commit `fde890c3`).

**This assembly pass.** To replace each "suggested disposition" with the real
one, this task originally re-read the `phase1-harden` tree at commit
`196c5f64` (HEAD after Task 9) directly — grepping and reading the files
Tasks 3–9 actually touched — rather than re-running any CLI tool, since no
fresh release APK matching the final Phase 1 diff existed yet at that time.
More than thirty citations below were individually re-verified against that
tree's file content and line numbers during this pass (spot-checking exceeds
the brief's "at least ten" requirement; the ones most likely to be wrong —
everything an auditor marked "fixed in Task N" or "NEW" — got priority).
Severity labels (`High`/`Medium`/`Low`/`Info`) and finding IDs are preserved
exactly as the auditors wrote them, with their file:line evidence; where the
code has moved since the audit, a **current** location is added.

**Reconciliation pass (I3, final whole-branch review's fix round).** Tasks
10, 12, 13, 15, 16 and 17 have since landed on `phase1-harden`, and the branch
HEAD moved well past Task 9 (see `git log phase1-harden`). This pass re-read
every row below whose disposition still said "Planned, Task N (not yet
executed)" against the current source tree and updated it to reflect what
actually landed, with fresh file:line citations. It also folds in the two
regressions the final review itself found and this fix round closed: **C1**
(`CookieVault.seal()` could never actually complete on a real Android
Keystore key — a new bug introduced by Task 7's own cookie-sealing work,
never previously audited, so it has no original audit ID; recorded below
under its own `C1` row) and **I1** (`BackupRestoreViewModel.restore()`'s
`prefs.clear(); prefs += restored` silently wiped the live sealed cookie and
account identity on every restore, contradicting Task 16's own plan text and
code comment — recorded as an amendment to A6.3/A10-3, the rows about the
same restore path). Rows this pass did not touch (because the reviewer who
requested this reconciliation said they were still fine to defer) are called
out explicitly where relevant rather than silently left stale.

**What "fixed" means below.** `Fixed in Task N` is only used when this pass
confirmed the change in the current source tree (file:line cited). `Planned,
Task N (not yet executed)` means a task exists in the plan with this finding
in scope but the task genuinely has not landed yet as of the most recent
reconciliation pass. `Accepted` means a named reason exists (a ledger ruling,
a design decision, or a negligible/no-exploit-path finding) and no further
work is planned. `Deferred to Phase 4` applies to Listen Together only.

## Residual risk (plain language)

This section is for a non-technical reader. It explains what is **still open right now**, today, on `phase1-harden` after Tasks 1–17 and the final whole-branch review's fix round — not a snapshot frozen at an earlier commit.

**What is already closed and solid:**
- The sign-in cookie is encrypted at rest with a hardware-backed key (Task 7), and — found and fixed only by this fix round's **C1** — it now actually seals correctly on a real phone's Keystore. Task 7's original code built its own IV and handed it to the Keystore, which a real device's Keystore rejects by default (`InvalidAlgorithmParameterException: "Caller-provided IV not permitted"`); every prior test used a plain-JCE stand-in that tolerated this, so the bug was invisible until an instrumented test ran against the real Android Keystore. **Before this fix, sign-in could never actually save the cookie on a real phone — every login attempt would have failed.** It is fixed now: `CookieVault.seal()` lets the Keystore generate the IV and reads it back, and an on-device test proves the round trip (see this fix round's report for the exact failing/passing evidence). A phone backup or a copied file still cannot be restored into the app and read back the cookie, because the app only trusts a cookie it sealed itself, and anything else gets wiped on the next start.
- Cloud backup and phone-to-phone transfer are both fully blocked (Tasks 4 and 6) — nothing about this app can leave the phone through Android's backup system anymore, including the Google sign-in cookies the WebView keeps.
- Any app on the phone used to be able to read the whole music library, see what's playing, and even make likes/searches happen on the family's YouTube account, with zero permissions. That is now closed (Task 8) — only the phone's own trusted apps (system UI, Bluetooth, the Assistant) and a cryptographically-verified Android Auto can control playback, and the denial log that proves this during Android Auto testing now actually prints in the release build family phones run (**I4**, this fix round — it used to be silenced by Task 17's own release-logging fix).
- The three home-screen widgets, music recognition, Discord, Last.fm, the in-app AI translator, and alarms are all gone — not just hidden, removed from the installed app (Tasks 3-5).
- The riskiest single item the auditors found — a mechanism that could download and run a complete, unsigned JavaScript program from the internet inside the app, with no signature check — has been switched off in code (Task 5) and the network path to it is also blocked (Task 12). It cannot run today.
- The Google sign-in session no longer sits in the WebView's cookie storage in plain text indefinitely (Task 15, this was the single highest-severity open item — finding A7.4), and a gap in that fix (a channel-switch helper that could leave a plaintext copy behind if the user backed out mid-switch) was found and closed this round too.
- Opening a backup file no longer probes it against YouTube before you confirm anything (Task 16 closed the main export/restore gap; this fix round removed the one remaining network probe in the preview screen — **I1 fold-in**).
- Restoring a backup used to silently sign you out — wiping your live session and account even though the backup never contained one to restore — because of a bug in Task 16's own restore code (**I1**). That is fixed: your current sign-in is now left alone by every restore, and a test proves it (restoring into a signed-in device keeps the cookie, only ordinary settings like theme change).
- Release builds no longer write detailed logs to the phone's system log (Task 17); this fix round additionally found that the ProGuard rule meant to strip these logs from the release binary never actually matched anything (a Kotlin compiler-shape mismatch) and fixed it, and moved one diagnostic log line so it actually appears in debug builds.
- The network allowlist that makes most network-based attacks moot by refusing to let the app talk to any host it doesn't need is in place (Task 12): `security/egress-allowlist.json` + `app/src/main/res/xml/network_security_config.xml`, proven on the emulator by `EgressPolicyInstrumentedTest`. A new test this round additionally proves no build variant's network config ever trusts a user-installed CA or has a `<debug-overrides>` block.

**What is still open, and why:**

1. **Listen Together's Settings-screen "Connect" button still has no code-level on/off switch.** The automatic "someone sent me a link" join is blocked (Task 5), and the network path is blocked (Task 12: `metroserverx.meowery.eu`/`metroserver.meowery.eu` are off the allowlist, so TLS to the family's server fails the handshake regardless of what the Connect button does). The code-level switch for the button itself is still Phase 4's job. **Expected to fully close:** Phase 4.
2. **The sign-in WebView's channel-switch cookie is still written without the `HttpOnly` flag** (A7.5), so a malicious page loaded during an active channel switch could in principle read it via `document.cookie` while the switch is in progress. This fix round narrowed the window (the cookie no longer persists past an abandoned switch, see C1/A7.4 above) but did not add `HttpOnly` itself — a cheap further hardening, not done yet.
3. **`fonts.googleapis.com` and a handful of other candidate hosts are still not on the egress allowlist**, and the login WebView's own sub-resource hosts are covered on paper but not yet confirmed against a real signed-in device — see `docs/pending-human-steps.md` for the device-verification checklist this needs.
4. **Listen Together's unbounded gzip-inflate bug (A13-1) and its unconditional trust in server data (A13-3) are unfixed in code** — both deferred to Phase 4 per the original audit's own disposition. The network path to reach them is blocked today (Task 12), which is why this is Low practical risk right now, not High.

None of the items above is something a stranger with no access to the phone can exploit over the network today.

**Added by the final whole-branch review and this fix round, outside the original four auditors' scope (no original finding ID):**

- **C1 (Critical, fixed).** `CookieVault.seal()` could never actually complete on a real Android Keystore key — a regression introduced by Task 7's own cookie-sealing code, invisible to every unit test because they all used a software (non-Keystore) stand-in key.
