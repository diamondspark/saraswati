# Saraswati Phase 1 security audit

This document assembles the findings of four independent, read-only security
reviews of the pinned Metrolist base (upstream `main` @ `76fa5a78`, InnerTubeX
`v0.8.4`) into one table per review area, replaces each auditor's *tentative*
disposition with the *real* one — verified against the code actually on
`phase1-harden` as of this task — and records what is still open today.

## Method

**Reviewers.** Four read-only area auditors (Claude, opus) reviewed the pinned
base commit on 2026-10-17, in parallel, with no ability to build, run or
modify anything (Ruling R9):

- **A — platform and IPC surface:** manifest, exported components, FileProvider,
  backup scope, `PendingIntent` flags, secrets in `BuildConfig`/resources.
- **B — web content, sign-in, untrusted input:** `LoginScreen.kt`'s WebView,
  `PoTokenWebView`, the cookie's lifecycle, the proxy setting, deep links.
- **C — data, backup/restore, logging, third-party libraries.**
- **D — YouTube engine, remote configuration, network host inventory** (also
  produced the standalone `host-inventory.md` appended below).

**Tools.** Each auditor's own method section (quoted in `audit/findings-*.md`)
states the review was static source reading with `rg`/`grep`/`sed`/`git grep`
over the app, the `innertube` module and the InnerTubeX `v0.8.4` source tree;
one check (Media3's `ControllerInfo` API surface) was done by `unzip`/`strings`
on a cached AAR, deleted afterwards. **Nothing was built, run or installed**
for the audit itself — no `rea-agents` CLI invocation appears in any of the
four method sections, despite the task brief describing that as the intended
evidence source; this is noted here rather than silently reconciled. Base
commits: app `76fa5a78b5110674442884b6f21c0cef51cdb782` (2026-10-08 upstream
date), InnerTubeX `v0.8.4` (commit `fde890c3`).

**This assembly pass.** To replace each "suggested disposition" with the real
one, this task re-read the *current* `phase1-harden` tree at commit `196c5f64`
(HEAD after Task 9) directly — grepping and reading the files Tasks 3–9
actually touched — rather than re-running any CLI tool, since no fresh release
APK matching the final Phase 1 diff exists yet (Tasks 12, 15–17 have not run).
More than thirty citations below were individually re-verified against current
file content and line numbers during this pass (spot-checking exceeds the
brief's "at least ten" requirement; the ones most likely to be wrong —
everything an auditor marked "fixed in Task N" or "NEW" — got priority).
Severity labels (`High`/`Medium`/`Low`/`Info`) and finding IDs are preserved
exactly as the auditors wrote them, with their file:line evidence; where the
code has moved since the audit, a **current** location is added.

**What "fixed" means below.** `Fixed in Task N` is only used when this pass
confirmed the change in the current source tree (file:line cited). `Planned,
Task N (not yet executed)` means a task exists in the plan with this finding
in scope but Tasks 12 and 15–17 have not run yet — HEAD is at Task 9. `Accepted`
means a named reason exists (a ledger ruling, a design decision, or a
negligible/no-exploit-path finding) and no further work is planned. `Deferred
to Phase 4` applies to Listen Together only.

## Residual risk (plain language)

This section is for a non-technical reader. It explains what is **still open right now**, today, on `phase1-harden` at commit `196c5f64` — not what the finished Phase 1 will look like once every task has run.

**What is already closed and solid:**
- The sign-in cookie is encrypted at rest with a hardware-backed key (Task 7). A phone backup or a copied file can no longer be restored into the app and read back the cookie, because the app only trusts a cookie it sealed itself, and anything else gets wiped on the next start.
- Cloud backup and phone-to-phone transfer are both fully blocked (Tasks 4 and 6) — nothing about this app can leave the phone through Android's backup system anymore, including the Google sign-in cookies the WebView keeps (see below).
- Any app on the phone used to be able to read the whole music library, see what's playing, and even make likes/searches happen on the family's YouTube account, with zero permissions. That is now closed (Task 8) — only the phone's own trusted apps (system UI, Bluetooth, the Assistant) and a cryptographically-verified Android Auto can control playback.
- The three home-screen widgets, music recognition, Discord, Last.fm, the in-app AI translator, and alarms are all gone — not just hidden, removed from the installed app (Tasks 3-5).
- The riskiest single item the auditors found — a mechanism that could download and run a complete, unsigned JavaScript program from the internet inside the app, with no signature check — has been switched off in code (Task 5). It cannot run today.

**What is still open, and why:**

1. **The Google sign-in session sits in the WebView's cookie storage in plain text, indefinitely, on the device.** This was rated High by the auditors (finding A7.4). It is not yet fixed — the fix is written into the plan as Task 15, which has not run yet. It cannot leave the device (backup/transfer are closed), but if the phone itself is ever compromised, lost unlocked, or imaged, this is a live Google account session, not just a YouTube cookie. **Expected to close:** when Task 15 runs.
2. **Opening a backup file still probes it against YouTube before you confirm anything.** Just tapping a backup file in the restore picker sends that file's cookie to YouTube's servers to show an account name — before you decide whether to restore it at all. **Expected to close:** when Task 16 runs.
3. **Listen Together can still be manually connected to the real, family-run server today**, even though the family isn't supposed to use it until Phase 4. The automatic "someone sent me a link" join is blocked (Task 5). But there is no on/off switch in the code for the Settings screen's own "Connect" button, and the network-level block that was supposed to make the server unreachable (Task 12) has not run yet. In practice this is low-urgency — nobody in the family is being told to use this screen, and the server is the family's own — but it means the "Listen Together is disconnected in Phase 1" claim in the design is not fully true yet. **Expected to close:** when Task 12 runs (network block) and, for full correctness, Phase 4 (feature itself).
4. **The sign-in WebView will still follow links to any website**, and the "Advanced login / Token" screen that shows your raw session as copyable text is still present (both rated Medium). Neither has been exploited by anything in this app's own code — the risk is a malicious web page reached through a link inside the sign-in flow, or someone social-engineering a family member into pasting a token. **Expected to close:** when Task 15 runs.
5. **Release builds still write detailed logs to the phone's system log**, including every song played and Listen Together room codes (not the cookie — that specific value is never logged). On a shared family phone this is a privacy nicety more than an account-takeover risk. **Expected to close:** when Task 17 runs.
6. **The network "allowlist" that would make all of the above moot by simply refusing to let the app talk to any host it doesn't need has not been built yet.** Tasks 1-9 closed the *code paths* to most of these risks; Task 12 closes the *network* as a second, independent layer underneath all of them. Until it runs, several of the mitigations above rely on code alone.

None of the six items above is something a stranger with no access to the phone can exploit over the network today — the worst-case items (1 and 3) require either physical access to the phone or a family member manually choosing to use a hidden-away screen. All six already have a task number and a planned fix; this document's job is to say plainly that the fix has not executed yet, not to invent a new one.
